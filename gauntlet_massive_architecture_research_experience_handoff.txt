GAUNTLET — MASSIVE ARCHITECTURE + RESEARCH + EXPERIENCE-COMPILER HANDOFF
Consolidated engineering handoff
Status: target architecture; extend the current Gauntlet, do not rewrite from scratch

======================================================================
0. EXECUTIVE MANDATE
======================================================================

Gauntlet should become the ultimate lightweight developer-intelligence runtime around coding agents.

It should have access to:
- deep workflow knowledge,
- strong implementation discipline,
- repository intelligence,
- code-structure understanding,
- technical documentation,
- expert domain references,
- long-horizon execution memory,
- verification strategies,
- browser evidence,
- optional delegation,
- and a growing body of validated experience.

But almost none of that should be active on an ordinary task.

The defining target is:

    BIG CAPABILITY SURFACE
    +
    SMALL ACTIVE WORKING SET

Or more simply:

    Know a lot. Load a little.

And:

    Put sophistication in selection, not in the default workflow.

The product should feel smaller than the coding agent it improves.

The normal experience must remain:

    install Gauntlet
    use coding agent normally
    Gauntlet quietly improves context / behavior / verification
    clean result
    verified result
    done

Gauntlet should not become:
- another coding agent,
- another IDE,
- another CI platform,
- a giant RAG stack,
- a vector-memory product,
- a mandatory methodology,
- a dashboard-first governance system,
- a multi-agent swarm framework,
- or a background daemon constantly watching the repository.

The core product value is:

    Gauntlet decides what additional engineering intelligence is worth using,
    when it is worth using,
    how deeply it should activate,
    what evidence is already enough,
    and when to stop.

2. PRODUCT IDENTITY
======================================================================

Gauntlet should evolve toward:

    A lightweight engineering runtime that understands the task,
    the repository,
    the current execution state,
    the available capabilities,
    and the evidence required to finish cleanly.

Another useful definition:

    Gauntlet is an adaptive control plane that gives coding agents
    the minimum additional intelligence needed to complete the current
    task cleanly.

And the strongest short framing remains:

    Ponytail for the entire development workflow.

Meaning:
- Ponytail makes agents write less.
- Gauntlet makes agents waste less.

Waste includes:
- unnecessary code,
- unnecessary context,
- unnecessary questions,
- repeated failed approaches,
- duplicate infrastructure,
- avoidable docs lookups,
- over-testing,
- under-testing,
- needless browser runs,
- unnecessary multi-agent work,
- overlong tool output,
- redundant file reads,
- avoidable repo rediscovery,
- carrying dead execution history forward,
- loading expert knowledge that does not affect the task,
- and verifying low-risk work with high-cost machinery.

3. CORE ENGINEERING CONSTITUTION
======================================================================

The following four rules should be nearly universal and extremely compact.
They should sit at the bottom of the hierarchy as Gauntlet’s small default engineering constitution.

3.1 REUSE BEFORE BUILD

Preferred ladder:

    Does new code need to exist?
    ↓
    Equivalent capability already in repo?
    ↓
    Can owning implementation be modified directly?
    ↓
    Can language / stdlib / framework / platform solve it?
    ↓
    Can installed dependency solve it?
    ↓
    Is there a mature, reliable, secure OSS capability?
    ↓
    Is there a supported extension point?
    ↓
    Only then create custom infrastructure.

Important nuance:
- Prefer reliable, secure OSS over reinvention.
- Prefer supported extension points over forks/custom replicas.
- Do not add a dependency when the repository already has an adequate primitive.
- Do not force external OSS when the existing local implementation is simpler and sufficient.
- “Reuse” includes repo-native capability, not only external packages.

3.2 MINIMUM SUFFICIENT SOLUTION

Choose the simplest solution that:
- satisfies the task,
- preserves required behavior,
- fits repository conventions,
- handles the real risk,
- and passes relevant evidence.

Avoid:
- speculative abstractions,
- future-proofing without a requirement,
- second implementations,
- generic frameworks for one use case,
- new APIs that no caller needs,
- broad refactors hidden inside feature work.

Stop when the acceptance criteria are met cleanly.

3.3 PROVE VERSION-SENSITIVE ASSUMPTIONS

Never guess an unfamiliar or version-sensitive API when cheap authoritative evidence can resolve it.

Resolution ladder:

    repo usage
    ↓
    installed types
    ↓
    installed source
    ↓
    package / lockfile version
    ↓
    local docs
    ↓
    official version-compatible docs
    ↓
    broader external search only if still necessary

This does NOT mean “always query docs.”
It means “do not rely on stale model memory when the machine can cheaply prove the current API.”

3.4 EVIDENCE, NOT TEST VOLUME

Write and run only the checks that provide meaningful confidence.

Ask:

    What meaningful uncertainty remains?
    ↓
    What is the cheapest evidence that can reduce it?
    ↓
    Run that.
    ↓
    Stop when more evidence is unlikely to change acceptance.

Avoid:
- redundant tests,
- giant release gates for small edits,
- always running the full suite,
- adding tests that do not distinguish old behavior from new behavior,
- “more tests = more confidence” thinking.

4. CORE PRODUCT PRINCIPLES
======================================================================

1. Know a lot. Load a little.
2. Store richly. Index cheaply. Select dynamically. Expand reluctantly.
3. Put sophistication in selection, not in the default workflow.
4. Machine first. Model second.
5. Memory for facts should be retrieved. Memory for work should be resumed.
6. Preserve the valid execution path. Quarantine failed branches.
7. Validate a boundary, shorten the horizon, then continue from the valid state.
8. Experience may accumulate freely. Behavior must earn promotion.
9. Rejected behavior changes are still useful knowledge.
10. Context should add information, not merely relevance.
11. Different evidence structures may be complementary; use the smallest useful combination.
12. Repository understanding should evolve incrementally from real work.
13. Impact should determine planning and verification depth.
14. External documentation is escalation, not default context.
15. The existence of a capability is not a reason to activate it.
16. Progress means uncertainty or evidence improved, not merely that more code was written.
17. Verification must prove both what changed and what must remain unchanged.
18. Skills control behavior; references provide expert knowledge; repo facts provide local truth; execution state provides current-task truth; evidence determines completion.
19. Discover before building.
20. Observe before modifying.
21. Existing debt may remain; new work should not quietly make it worse.
22. If a rule matters enough to constrain the agent, make it machine-checkable when cheap.
23. Verify before completion, but stop once enough evidence exists.
24. No second agent unless measured evidence says it is worth the cost.
25. Silence is a first-class successful behavior.
26. Every major subsystem requires:
    - a cheap path,
    - an escalation trigger,
    - a stop condition,
    - and eval evidence that it earns its cost.
27. Gauntlet can know far more than it ever shows the agent.

5. CURRENT ARCHITECTURE PROBLEM
======================================================================

The current Gauntlet direction contains several useful selectors:

- initial skill routing,
- dynamic intervention selection,
- capability selection,
- verification selection,
- domain resolution,
- context selection.

Individually, these can all be smart.

Collectively, they risk becoming:

    five or six intelligent systems
    that do not share one final activation decision.

That creates:
- redundant activation,
- conflicting policies,
- duplicated context,
- unnecessary cost,
- unclear responsibility.

The next architectural priority is therefore not “add more features.”

It is:

    SPECIALIZED SUBSYSTEMS GENERATE CANDIDATES
    ONE CONTROL PLANE DECIDES WHAT ACTUALLY ACTIVATES

Subsystems still own specialized logic.

Control owns:
- competition,
- deduplication,
- dominance elimination,
- budgeting,
- activation,
- deactivation,
- escalation,
- and final composition.

======================================================================
7. UNCERTAINTY-FIRST CONTROL
======================================================================

Gauntlet should operate from uncertainty, not tools.

Bad mental model:

    Should I load a skill?
    Should I query docs?
    Should I use the graph?
    Should I open a browser?
    Should I delegate?

Correct mental model:

    What could still make this task wrong?

Use a small uncertainty taxonomy:

INTENT
What does the developer actually require?

LOCATION
Where does the relevant behavior live?

CAUSE
Why is the observed failure occurring?

REPO_FIT
How should this repository solve the concern?

API
What does the installed dependency / platform actually support?

BEHAVIOR
Does the requested behavior work?

REGRESSION
What existing behavior could break?

SCOPE
Is the implementation doing more than required?

VISUAL
Does rendered behavior satisfy the requirement?

PERFORMANCE
Where is the meaningful cost?

Do not invent dozens of uncertainty types.

These are observable state labels, not chain-of-thought.

Example:

type UncertaintyState = {
  intent: "resolved" | "open";
  location: "resolved" | "partial" | "open";
  cause: "irrelevant" | "resolved" | "open";
  repoFit: "resolved" | "open";
  api: "resolved" | "open";
  behavior: "resolved" | "open";
  regression: "resolved" | "open";
  scope: "resolved" | "open";
  visual: "irrelevant" | "resolved" | "open";
  performance: "irrelevant" | "resolved" | "open";
};


======================================================================
8. SHARED ESCALATION LADDER
======================================================================

Use roughly the same escalation model across Gauntlet:

L0
Already known / cached.

L1
Cheap deterministic local evidence.

L2
Targeted local search / check / structural query.

L3
Specialized skill / reference / provider.

L4
Runtime or external evidence.

L5
Expensive reasoning / delegated work.

Most tasks should remain at L0–L2.

L4–L5 should be rare.

Do not use a magical routing score like:

    intervention usefulness = 87.4

Prefer understandable elimination:

    already resolved?
    → reject

    not relevant?
    → reject

    cheaper authoritative source available?
    → reject expensive source

    same information already present?
    → reject duplicate

    exceeds budget?
    → defer unless risk justifies escalation

9. UNIFIED ACTIVATION MODEL
======================================================================

Introduce one shared candidate representation.

Conceptually:

type ActivationCandidate = {
  id: string;

  kind:
    | "skill"
    | "context"
    | "evidence"
    | "capability"
    | "reference"
    | "graph-expansion";

  resolves: UncertaintyKind[];

  cost: "tiny" | "low" | "medium" | "high";

  authority:
    | "cached"
    | "repo"
    | "local"
    | "runtime"
    | "external";

  source: string;

  reason: string;
};

Subsystems produce candidates.
They do not independently force activation.

Control outputs:

type ActivationPlan = {
  skill?: SkillName;
  context: ContextRequest[];
  evidence: EvidenceRequest[];
  capabilities: CapabilityRequest[];
  references: ReferenceRequest[];
  graphExpansions: GraphRequest[];
};

For an ordinary task, typical result should be:

    skill             0–1
    context expansion 0–2
    capabilities      0
    special refs      0
    expensive checks  0

10. SELECTION ALGORITHM
======================================================================

Conceptually:

    OBSERVE
    task
    repo
    execution state
    active branch
    uncertainty
    working graph
    diff
    failures
    available capabilities
    evidence already held

    ↓

    GENERATE CANDIDATES

    workflow candidates
    context candidates
    graph candidates
    knowledge candidates
    verification candidates
    provider candidates

    ↓

    ELIMINATE

    irrelevant
    already resolved
    duplicate
    unavailable
    dominated
    over budget

    ↓

    CHOOSE MINIMAL COMPLEMENTARY SET

The word complementary matters.

The correct answer is not always:
- one evidence structure,
- or all evidence structures.

A debugging task may need:

    active execution path
    +
    failing test
    +
    small code neighborhood

An API question may need only:

    installed type declaration

The selector should choose the smallest combination that resolves the uncertainty.

12. PROGRESSIVE DISCLOSURE EVERYWHERE
======================================================================

Every substantial evidence source should support:

REFERENCE
Identifier only.

CONCISE
Small fact / summary.

DETAILED
Underlying evidence.

Example:

REFERENCE
src/lib/retry.ts

CONCISE
Shared retry primitive used by 7 modules.

DETAILED
Exports, callers, relevant implementation range.

Default to reference or concise.

Expand only while uncertainty remains.

This principle should apply to:
- code,
- memory,
- repository facts,
- docs,
- test output,
- browser output,
- domain references,
- historical lessons.

The agent should not receive full content simply because Gauntlet knows it exists.


======================================================================
13. HIGH-LEVEL AGENT TOOLS
======================================================================

Agent-facing tools should represent meaningful developer operations, not internal implementation primitives.

Bad:

    graph_get_file
    graph_get_symbol
    graph_get_imports
    graph_get_callers
    graph_get_tests

Prefer:

    inspect_impact(target)

Returning:

    owner
    dependencies
    dependents
    tests
    public surface
    relevant boundaries

Low-level graph operations remain internal deterministic implementation details.

Similarly, avoid exposing:
- dozens of capability wrappers,
- provider-specific mechanics,
- internal cache operations.

The agent should see one useful operation, not the machinery.

14. WORKFLOW PLANE
======================================================================

Keep exactly six top-level skills:

UNDERSTAND
INVESTIGATE
IMPLEMENT
VERIFY
REVIEW
OPTIMIZE

Do not create dozens of narrow top-level skills.

Browser testing, mutation testing, security, frontend design, Postgres, React, MCP, prototypes, SEO, performance, debugging, component libraries, and similar concerns should live as:
- specialist references,
- techniques,
- provider capabilities,
- evidence mechanisms,
under the six stable skills.

Core detects WHEN.
Skill defines HOW.


======================================================================
15. SKILL PROMPT PHILOSOPHY
======================================================================

Do not make skills artificially tiny.

Make them:
- dense,
- explicit,
- ordered,
- behaviorally precise,
- low-fluff.

A skill may be hundreds of tokens if every sentence changes a real engineering decision.

Avoid:
- “You are world-class.”
- “Think deeply.”
- persona fluff.
- motivational framing.
- identity theater.

Use structure like:

    clear purpose
    decision hierarchy
    preferred behavior
    anti-patterns
    correctness boundaries
    stopping condition

Lightweightness comes from:
- loading only one relevant skill,
not from:
- making every skill weak.


======================================================================
16. DYNAMIC WORKFLOW TRANSITIONS
======================================================================

Skill selection must not be task-start-only.

Example:

    ordinary bug
    ↓
    IMPLEMENT
    ↓
    same failure repeats
    ↓
    INVESTIGATE
    ↓
    cause established
    ↓
    IMPLEMENT
    ↓
    machine verification

Useful transition signals:

- repeated failure,
- same function repeatedly rewritten,
- diff grows without evidence improvement,
- public surface appears in diff,
- new test appears,
- visual files change,
- migration appears,
- performance measurement appears,
- root cause becomes validated,
- current branch stalls.

Skills should unload when phase ends.

Example:
- INVESTIGATE should not remain active after root cause is established.
- VERIFY should not be loaded if deterministic evidence already establishes completion.


======================================================================
17. SKILL BEHAVIOR SUMMARIES
======================================================================

UNDERSTAND
- inspect existing context before asking,
- derive the smallest task contract,
- identify preserved behavior,
- do not invent requirements,
- ask one focused question only when guessing is materially expensive,
- avoid mandatory brainstorm/spec ceremony.

INVESTIGATE
- observe/reproduce first when practical,
- find root cause before editing symptoms,
- distinguish fact from assumption,
- stop when cause is sufficiently supported,
- escalate only if simple inspection fails.

IMPLEMENT
- reuse before creating,
- follow repo conventions,
- stay task-scoped,
- avoid speculative abstractions,
- avoid unneeded dependencies,
- verify unfamiliar APIs,
- do not weaken tests.

VERIFY
- ask what uncertainty remains,
- gather the cheapest useful evidence,
- stop when further evidence is unlikely to change acceptance.

REVIEW
- inspect final diff only,
- focus on issues introduced by this task,
- flag scope drift, duplicate capability, unnecessary abstraction, dependency growth, rule drift, test weakening, public API growth, dead code, complexity.

OPTIMIZE
- measure,
- find dominant cost,
- change smallest relevant cause,
- measure again,
- do not optimize from intuition alone.


======================================================================
18. TASK CONTRACT
======================================================================

At task start derive a tiny internal contract from:
- user request,
- acceptance criteria,
- AGENTS.md / CLAUDE.md / repo instructions,
- tests,
- obvious preserved behavior.

Example:

Goal:
Prevent duplicate refresh requests.

Preserve:
Public API and AuthError behavior.

Acceptance:
Concurrent refresh calls trigger one actual refresh.

Do not ask the user to restate what the repo can establish itself.


======================================================================
19. EXECUTION-STATE MEMORY
======================================================================

Do not treat long-running task memory as semantic retrieval over conversation history.

Use:

    execution state with explicit valid and rejected branches

Core principle:

    Memory for facts should be retrieved.
    Memory for work should be resumed.

Separate two forms of memory:

REPOSITORY / TECHNICAL MEMORY
Facts and structure.
Good for lookup / search / graph retrieval.

TASK EXECUTION MEMORY
Path-dependent decisions and evidence.
Should use active-path reconstruction.

Do not collapse them into one “memory” system.


======================================================================
20. EXECUTION TREE
======================================================================

Represent a task as a lightweight checkpoint tree.

Example:

TASK ROOT
│
├── understanding ✓
│
├── investigation ✓
│
├── implementation A ✗
│   └── rejected:
│       process-local locking is insufficient
│
└── implementation B ← ACTIVE
    ├── reuse existing coalescing primitive
    └── verification pending

The normal model context receives the current valid root-to-active path.

It does NOT receive:
- the full failed branch,
- every shell command,
- every stale hypothesis,
- all old tool chatter.


======================================================================
21. THREE-LAYER TASK MEMORY
======================================================================

Use:

RAW EVIDENCE
commands / logs / diffs / tool output

↓

EXECUTION EVENTS
small structured records

↓

CHECKPOINT TREE
meaningful validated / rejected states

Model context primarily consumes:

    active checkpoint path
    +
    recent high-value events

Raw evidence remains retrievable.


======================================================================
22. CHECKPOINT BOUNDARIES
======================================================================

Do not create checkpoints for every action.

Create only when task state materially changes.

Good boundaries:
- task interpretation settled,
- important constraint established,
- root cause supported,
- design direction chosen,
- approach rejected,
- implementation ready for verification,
- verification established,
- verification materially failed.

Checkpoint types may include:

type CheckpointKind =
  | "task"
  | "understanding"
  | "investigation"
  | "decision"
  | "implementation"
  | "verification";

type CheckpointStatus =
  | "active"
  | "validated"
  | "rejected";


======================================================================
23. REAL AGENT-TO-GAUNTLET STATE REPORTING
======================================================================

Meaningful checkpoint transitions must be reachable in normal harness use.

Do not rely only on low-level observed events like:
- file read,
- file write,
- command,
- message.

Provide a tiny internal state-report mechanism:

reportState({
  kind: "cause",
  summary: "Concurrent refresh requests lack coalescing.",
  evidenceRefs: [...]
});

Possible kinds:
- understanding,
- cause,
- decision,
- rejection,
- implementation,
- verification.

This should be:
- developer-invisible,
- rare,
- structured,
- adapter-translated.

Different harnesses may implement via:
- native tool,
- hidden command,
- structured hook,
- small internal tool call.

Core only understands:
- “report meaningful state boundary.”


======================================================================
24. FAILED-BRANCH QUARANTINE
======================================================================

Do not erase failed branches.
Do not mix them into current state.

Preserve:
- approach,
- reason rejected,
- evidence.

Surface a failed branch only if current work begins to repeat it.

Example:

Current direction overlaps a previously rejected approach.

A second retry abstraction was rejected because
src/lib/retry.ts already owns retry behavior.

Reassess before creating another implementation.

This is much better than semantic retrieval accidentally resurfacing a failed path merely because it is relevant.


======================================================================
25. HORIZON REDUCTION
======================================================================

Validated checkpoints should reduce the effective problem horizon.

Example:

large debugging task
↓
investigation
↓
CAUSE VALIDATED
════════════════
new compact state
↓
implementation
↓
IMPLEMENTATION VALIDATED
════════════════
new compact state
↓
verification

After each validated boundary:
- resume from compact valid state,
- do not make the model reason over the entire historical transcript.


======================================================================
26. STABLE STATE VS LIVE PROGRESS
======================================================================

Separate:

STABLE TASK STATE
- goal,
- acceptance criteria,
- constraints,
- validated facts,
- important decisions.

LIVE PROGRESS STATE
- active branch,
- current approach,
- open uncertainties,
- recent failures,
- last evidence delta,
- current working set.

Stable state changes slowly.
Progress state changes frequently.

This separation improves:
- compaction,
- task handoff,
- delegation,
- debugging,
- persistence.


======================================================================
27. PROGRESS-DELTA TRACKING
======================================================================

Loop detection should not depend only on repeated identical failures.

At meaningful boundaries compare:

    uncertainty before → after
    evidence before → after
    implementation scope before → after

Classify:

PROGRESS
STALLED
REGRESSED

No numeric quality score required.

Example stalled branch:

    three edits
    +
    diff grew
    +
    same uncertainty remains
    +
    no new evidence

Result:

    branch stalled
    → reconsider assumption
    → INVESTIGATE / revise branch

This should happen before uncontrolled looping.


======================================================================
28. EXECUTION-AWARE COMPACTION
======================================================================

Do not summarize history chronologically.

Ask:

    Which completed section of the current valid execution path
    is stable enough to collapse?

Before:
- 14 file reads,
- 6 commands,
- 3 hypotheses,
- 2 failed edits,
- root-cause confirmation.

After:

CAUSE ESTABLISHED

Failure:
Concurrent refresh callers independently invoke token refresh.

Cause:
Refresh operation lacks request coalescing.

Relevant:
src/auth/session.ts
src/lib/singleflight.ts

Rejected:
Process-local mutex because coordination scope is insufficient.

Evidence:
race reproduction.

Raw evidence remains on disk.

Preserve:
- goal,
- acceptance,
- constraints,
- validated facts,
- current approach,
- relevant code,
- remaining uncertainty,
- useful rejected direction,
- evidence refs.

Drop:
- superseded hypotheses,
- resolved compiler errors,
- repeated searches,
- repeated reads,
- obsolete implementation details,
- raw terminal chatter.


======================================================================
29. EXPERIENCE COMPILER
======================================================================

Add a slower, cross-task learning loop inspired by experience-to-skill compilation.

Do NOT run this heavy process inside normal user tasks.

Normal development loop:

    agent works
    ↓
    Gauntlet preserves:
      events
      checkpoints
      evidence
      outcomes
      selection traces
      rejected branches

Offline / eval evolution loop:

    sample useful trajectories
    ↓
    extract recurring:
      failures
      successful strategies
      bad interventions
      good interventions
    ↓
    update persistent knowledge
    ↓
    propose ONE atomic behavior change
    ↓
    run Gauntlet eval suite
    ↓
    better?
      yes → retain
      no  → rollback behavior change

Important:
- accumulated knowledge survives,
- a rejected behavior proposal does not erase the knowledge that produced it.

Core principle:

    Experience may accumulate freely.
    Behavior must earn promotion.

And:

    Rejected behavior changes are still valuable knowledge.


======================================================================
30. FOUR KNOWLEDGE LAYERS
======================================================================

Keep these distinct:

RAW EXPERIENCE
Immutable traces / evidence.

TASK EXECUTION STATE
Current valid path and rejected branches.

PERSISTENT KNOWLEDGE
Cross-task verified patterns.

PROCEDURAL BEHAVIOR
Skills, selector rules, verification policies, context policies.

Do not collapse all of these into one memory store.

======================================================================
32. WHAT EXPERIENCE MAY CHANGE
======================================================================

Cross-task experience should not only mutate skills.

Possible atomic proposal types:

SKILL CHANGE
Example:
INVESTIGATE should explicitly verify empty search results.

SELECTOR CHANGE
Example:
Repeated rewrite + unchanged evidence should trigger INVESTIGATE sooner.

REPO RULE CHANGE
Example:
This repository consistently routes DB access through repositories.

EVIDENCE POLICY CHANGE
Example:
Public API changes need downstream consumer verification.

CONTEXT POLICY CHANGE
Example:
This evidence view repeatedly adds no useful information.

REFERENCE CHANGE
Example:
Add a verified Postgres concurrency rule.

Exactly one atomic proposal per experiment when possible.

Reason:
- attribution becomes possible,
- rollback becomes clean,
- eval results are interpretable.


======================================================================
33. BRANCH-DERIVED LESSONS
======================================================================

Sometimes compare:

vs
successful branch

If one concrete difference clearly explains success, produce a candidate lesson.

Example:

Succeeded:

- clear evidence,
- stable scope,

- eval benefit if behavior changes.

34. THREE TIMESCALES
======================================================================

Gauntlet now has three distinct timescales:

MILLISECONDS / SECONDS
CONTROL

======================================================================
35. MODEL-INDEPENDENT PRODUCT IP
======================================================================

A useful engineering procedure discovered while one coding model is active can be:
- validated,
- distilled,
- stored in Gauntlet,
- then reused by other coding models later.

This means Gauntlet’s long-term value can become:
- model-independent engineering procedure,
- selection policy,
- repository understanding,
- evidence policy,
- validated expert knowledge.

Do not share raw transcripts across models.

======================================================================
40. OUTPUT CONDITIONING
======================================================================

Output conditioning should remain first-class because it can produce negative net token cost.

Example:

skill guidance        +500 tokens
compressed test logs -8000 tokens

Net:
-7500 tokens

Do not merely truncate.

Extract:
- exit code,
- summary,
- unique failures,
- relevant file/line,
- first useful stack frame,
- important warnings.

Store full raw output separately.

Example model-visible output:

Tests:
184 passed
2 failed

Failures:
session.test.ts — expiry boundary
retry.test.ts — expected 3 calls, got 4

Raw:
run-output:42

The evidence ref can be attached to checkpoints.

Principle:

    Compress context, not evidence.


======================================================================
41. ADDRESSABLE KNOWLEDGE
======================================================================

Every knowledge item should conceptually have an address before content.

Possible conceptual addressing:

    repo://primitive/http
    code://src/auth/session.ts#refresh
    evidence://run/42/failure/1
    knowledge://zod/4/discriminated-union

- stable reference first,
- concise fact second,

======================================================================
42. CODE INTELLIGENCE PLANE
======================================================================

Gauntlet should understand repository structure natively.

Do NOT begin with:
- embeddings,
- vector DB,
- always-on graph server,
- giant semantic summaries,
- whole-repo AI-generated knowledge graph.

Start deterministic and progressive.

43. LEVEL 1 CODE INTELLIGENCE
======================================================================

Persist:

- files,
- content hashes,
- imports,
- exports,
- directory/package boundaries,
- test relationships.

Answer cheaply:

- what imports this?
- what does this depend on?
- what tests are nearby?
- is this public?
- what package owns it?


======================================================================
44. LEVEL 2 CODE INTELLIGENCE
======================================================================

Add symbols:

- functions,
- classes,
- methods,
- types,
- interfaces,
- constants.

Edges:

- defines,
- references,
- calls,
- exports,
- implements,
- extends,
- tested-by.

Prefer:
- language tooling,

Do not:

======================================================================
45. LEVEL 3 CODE INTELLIGENCE
======================================================================

Only when required:

- likely duplicate capability,
- behavior ownership,
- architecture boundary,
- unexpected dependency path,
- semantic overlap.

Resolution order:

    cheap heuristics
    ↓
    structural evidence
    ↓
    model reasoning only if unresolved

Rare by default.


======================================================================
46. PERSISTENT SHALLOW INDEX
======================================================================

Do not repeatedly rebuild structural slices from dozens or hundreds of files.

Persist:

    .gauntlet/
      index/
        files.json
        edges.json
        symbols.json

On task start:

    load cached index
    ↓
    check fingerprints
    ↓
    update changed files only

No DB initially.

No daemon.

No full rescan unless:
- index missing,
- repository small enough,
- cold setup cost justified.


======================================================================
47. PROGRESSIVE GRAPH DEPTH
======================================================================

Introduce conceptually:

    ensureDepth(target, depth)

Possible levels:

FILE
files/imports/exports.

SYMBOL
functions/classes/types.

RELATION
references/callers/tests.

SEMANTIC
ownership / duplicate capability / higher-order patterns.

Most tasks should stop at FILE or SYMBOL.

SEMANTIC should be rare.


======================================================================
48. GRAPH CONFIDENCE
======================================================================

Treat structural evidence according to provenance.

Examples:

→ strong

→ medium

→ medium

regex call guess
→ weak

If a high-risk decision depends on a weak edge:
- verify through stronger evidence.

50. CODE GRAPH VS EXECUTION TREE
======================================================================

Keep them distinct.

EXECUTION TREE

Gauntlet joins them only for the task:

    ↓
    current uncertainty
    ↓

    ↓

Do not build one giant graph for everything.

======================================================================

    1 caller

65. SPECIALIST PERSPECTIVES WITHOUT SPECIALIST AGENTS
======================================================================

Before spawning multiple agents, try the cheap version:

Task touches:

Selector retrieves:
3 relevant database constraints
+
2 relevant authorization constraints

Deduplicate.

Inject one compact packet.

Example:

• Existing writes use the repository transaction boundary.
• Authorization must be enforced at the data-access boundary.
• New uniqueness invariant should use database enforcement where supported.

Verification:

• authorized write succeeds
• unauthorized write fails
• concurrent duplicate write cannot violate uniqueness

This gives multiple expert perspectives without:
- multiple transcripts,
- multi-agent coordination,
- synthesis overhead.

Only spawn a worker when independent reasoning is genuinely valuable.

======================================================================
74. DELEGATION
======================================================================

Gauntlet is not multi-agent by default.

Delegate only when:
- subtask is independently scoped,
- handoff context is small,
- merge-conflict risk is low,
- parallelism or isolation has real benefit,
- coordination cost is lower than direct work.

Default:
0 workers.

Initial maximum:
1 worker.

No hierarchy.

No multi-agent debate.


======================================================================

======================================================================

Worker gets:

- goal,
- current validated checkpoint,
- acceptance criteria,
- constraints,
- relevant code neighborhood,
- repo rules,
- expected deliverable.

Not:
- entire transcript.

Worker returns:

- status,
- result,
- evidence,
- changed files,
- blocker.

Parent owns final acceptance.

Worker success claim is evidence, not truth.

======================================================================

    ↓

    ↓

    ↓

======================================================================
78. RISK-AWARE EVIDENCE
======================================================================

Do not map:

uncertainty type
→ mandatory heavy check

without considering:

    uncertainty
    +
    impact
    +
    task type
    +
    available evidence
    +
    change kind
    +
    preservation requirements

Example low-risk regression uncertainty:

Acceptable:
- typecheck,

Do not block forever because no behavioral test exists.

Example high-risk regression uncertainty:

- affected tests,

======================================================================
79. PRESERVATION EVIDENCE
======================================================================

Verification should explicitly model:

CHANGE
What must become different?

PRESERVE
What must remain unchanged?

Example:

Goal:
replace parser implementation

Preserve:
public API
error semantics
serialized output

VERIFY should gather evidence for both.

Especially important for:
- refactors,
- performance work,
- security hardening,
- migrations,
- dependency replacement.


======================================================================
80. COUNTERFACTUAL TEST EVIDENCE
======================================================================

For valuable new behavior-specific tests, when safe:

    new test
    ↓
    run against old / broken behavior
    ↓
    should fail
    ↓
    run against fixed behavior
    ↓
    should pass

If:
old passes
new passes

Then:
evidence is weak.

Use selectively.

Do not force if:
- unsafe,
- expensive,
- environment not reproducible.


======================================================================
81. BEFORE-STOP GATE
======================================================================

First-class completion flow:

    agent requests stop
    ↓
    inspect active execution path
    ↓
    final diff
    ↓
    impact cone
    ↓
    active repo rules
    ↓
    baseline deltas
    ↓
    test integrity
    ↓
    preservation requirements
    ↓
    cheapest remaining evidence
    ↓
    meaningful uncertainty resolved?

If yes:
DONE.

If no:
one concise correction / evidence packet.

Example:

Completion blocked:

1. New route bypasses the repository-layer convention.
2. Regression test also passes against pre-change behavior.

Fix these only.

Default automatic correction:
0–1.

No endless repair loops.


======================================================================
82. MACHINE FIRST, MODEL SECOND
======================================================================

Preferred order:

    cached evidence
    ↓
    diff
    ↓
    repo rules
    ↓
    static checks
    ↓
    affected tests
    ↓
    runtime evidence
    ↓
    semantic VERIFY guidance
    ↓
    extra model / delegation

Do not ask a model what the compiler can prove.


======================================================================
83. PROACTIVITY POLICY
======================================================================

Gauntlet must decide not only what to detect, but whether a detected insight is worth surfacing.

Before interrupting:

    evidence strength
    +
    task relevance
    +
    expected actionability

If an issue is:
- weak,
- unrelated,
- unlikely to change the current task,

stay silent.

The product should not become a constant unsolicited reviewer.


======================================================================
84. HUMAN-INTERRUPTION POLICY
======================================================================

Ask the developer only when:

    uncertainty is material
    +
    multiple plausible choices lead to meaningfully different outcomes
    +
    repository evidence cannot resolve it
    +
    guessing is more expensive than asking

Ask one focused question.

Do not interview users.

Humans should generally own:
- product intent,
- irreversible tradeoffs,
- meaningful policy choices.

    TASK START
    ↓
    cheap classification / uncertainty
    ↓
    tiny repo + state packet
    ↓

    ↓
    agent works normally
    ↓
    cheap passive observation
    ↓
    meaningful state boundary?
    ↓
    checkpoint if needed
    ↓
    BEFORE STOP
    ↓
    relevant rules / baselines / evidence
    ↓
    done

Frequency:

EVERY TASK, CHEAP
- task/session IDs,
- classification,
- cached repo profile,
- stable/live state,
- maybe output conditioning,
- basic stop path.

SOMETIMES
- one skill,
- relevant repo rules,
- impacted verification,

RARELY
- specialist reference,
- browser,
- external docs,
- counterfactual test,

VERY RARELY

- delegation,
- broad E2E,

96. EVAL PHILOSOPHY
======================================================================

Gauntlet must be evaluated for both:

INTELLIGENCE
Did it help?

RESTRAINT
Did it stay quiet when it should?

A selector that always activates useful things is still bad if:
- it wastes tokens,
- adds latency,
- distracts the agent,
- over-verifies,
- over-asks,
- or activates redundant systems.


======================================================================
97. NORTH-STAR METRIC
======================================================================

Primary:

CLEAN FIRST-PASS SUCCESS (CFPS)

A task counts only if:

- requested behavior works,
- existing behavior remains intact,
- implementation fits repo conventions,
- unnecessary complexity/debt was not introduced,
- relevant evidence passes,
- no repair cycle was needed.

Other major metrics:

- Verified Completion Time,
- Cost per Verified Task,
- Attempts / revisions,
- LoC / files / dependencies,
- Tokens / cost where available,
- Gauntlet overhead,
- Human intervention.

114. HISTORICAL EVAL GENERATION
======================================================================

Later, derive evals from real git history.

Conceptually:

    known merged change
    ↓
    recover pre-change state
    ↓
    derive task
    ↓
    retain known-good final change
    ↓
    validate environment
    ↓
    run baseline
    ↓
    run Gauntlet

This should remain an internal development/eval tool first.

Do not build a giant benchmark platform.


======================================================================
115. EXPERIENCE-COMPILER EVAL LOOP
======================================================================

Use real eval tasks to validate any learned behavior change.

Loop:

    traces
    ↓
    persistent knowledge
    ↓
    one candidate change
    ↓
    eval suite
    ↓
    compare baseline
    ↓
    keep / rollback

The persistent knowledge should survive even when the candidate change is rejected.

Example:

Proposal:
Activate INVESTIGATE after every failed test.

Eval result:
Too many false activations.

Rollback proposal.

Keep knowledge:
A single failure is insufficient evidence for investigation escalation.

This prevents the system from rediscovering the same bad meta-policy.

- execution-state tree,

124. ARCHITECTURE ACCEPTANCE SCENARIOS
======================================================================

SCENARIO A — README TYPO

Expected:
- no skill,
- no graph expansion,
- no docs,
- no domain ref,
- no browser,
- no delegation,
- cheap diff/static check.

SCENARIO B — REPEATED FAILURE

Normal IMPLEMENT task.
Behavioral failure persists.

Expected:
- progress becomes STALLED,
- active branch reconsidered,
- INVESTIGATE activates,
- no task restart.

SCENARIO C — API UNCERTAINTY

Agent proposes unfamiliar API.

Expected:
- repo usage,
- installed types,
- resolved,
- no external docs.

SCENARIO D — FAILED BRANCH CONTAMINATION

Attempt A rejected.
Attempt B active.

Expected context:
- validated path,
- current B.

Not:
- full A transcript.

A warning about A appears only if B repeats it.

SCENARIO E — BROAD PUBLIC CHANGE

Public symbol has many dependents.

Expected:
- larger impact cone,
- compact change frontier if needed,
- stronger verification.

Not:
- arbitrary full-repo planning.

SCENARIO F — DUPLICATE HELPER

Agent starts creating retry helper.

Expected:
- existing capability discovered,
- one small reuse hint,
- no huge graph dump.

SCENARIO G — VISUAL FEATURE

VISUAL uncertainty survives implementation.

Expected:
- browser activates only then,
- one inspection,
- one confirmation if necessary.

SCENARIO H — LONG BUG WITH WRONG TURN

Expected:
- rejected implementation branch preserved,
- valid cause retained,
- new branch starts from valid boundary,
- failed history not reintroduced.

SCENARIO I — EXPERIENCE EVOLUTION

Repeated tasks reveal one recurring failure pattern.

Expected:
- persistent knowledge entry,
- one atomic selector/skill/reference proposal,
- eval,
- keep or rollback,
- knowledge survives either outcome.

133. FINAL PRODUCT IDENTITY
======================================================================

Gauntlet should not become:

    Superpowers
    + Context7
    + CodeGraph
    + memory
    + browser
    + expert personas
    + multi-agent orchestration

all running simultaneously.

That would be a bad product.

The target is:

    The useful intelligence of all of those categories
    under one adaptive, evidence-driven runtime
    that activates only the minimum required
    for the current engineering problem.

The value is not merely that Gauntlet contains powerful systems.

The value is that Gauntlet knows:

- which intelligence matters,
- when it matters,
- how deeply it should activate,
- what has already been established,
- which paths have already failed,
- what evidence is still missing,
- what additional context is redundant,
- what capability is dominated by a cheaper one,
- and when to stop.


======================================================================
134. FINAL GOVERNING RULES
======================================================================

Know a lot. Load a little.

Store richly. Index cheaply. Select dynamically. Expand reluctantly.

Put sophistication in selection, not in the default workflow.

Memory for facts should be retrieved. Memory for work should be resumed.

Preserve the valid execution path. Quarantine failed branches.

Validate a boundary, shorten the horizon, then continue from the valid state.

Experience may accumulate freely. Behavior must earn promotion.

Rejected behavior changes are still useful knowledge.

Context should add information, not merely relevance.

Different evidence structures may be complementary; use the smallest useful combination.

Skills control behavior.

References supply expert knowledge.

Repository facts supply local truth.

Execution state supplies current-task truth.

Code intelligence supplies structure.

Technical knowledge resolves API/platform uncertainty.

Evidence determines completion.

Use deterministic evidence before model reasoning.

Discover before building.

Observe before modifying.

Reuse before creating.

Build repository understanding progressively from actual tasks.

External documentation is escalation, not default context.

A useful provider does not need to activate merely because it exists.

Impact should determine planning and verification depth.

Progress means uncertainty or evidence improved, not that more code was written.

Verification must prove both desired change and preserved behavior.

Delegation is a rare optimization.

Silence is a first-class successful behavior.

Real engineering tasks should decide whether Gauntlet’s architecture is actually useful.

Every major subsystem must have:
- a cheap path,
- an escalation trigger,
- a stop condition,
- and an eval proving it earns its cost.

And above all:

    Gauntlet can know far more than it ever shows the agent.

The ultimate Gauntlet should have a huge engineering brain
with an extremely small working memory.
