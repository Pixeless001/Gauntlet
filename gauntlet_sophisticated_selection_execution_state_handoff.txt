GAUNTLET — SOPHISTICATED SELECTION + EXECUTION-STATE INTELLIGENCE HANDOFF

0. Scope

Extend the existing Gauntlet implementation.

Do not rebuild the product from scratch.

Do not replace working lifecycle, verification, repository profiling, output conditioning, skills, harness adapters, or completion enforcement merely to match this document.

This expansion has one central objective:

Give Gauntlet a very large available intelligence surface while keeping the active runtime extremely small.

Gauntlet should eventually contain deep workflow knowledge, repository intelligence, technical references, code relationships, execution memory, verification capabilities, browser evidence, and optional delegation.

But a normal development task should use almost none of it.

Core principle:

Know a lot. Load a little.

And:

Put sophistication in selection, not in the default workflow.

2. Product direction

Gauntlet should become:

A lightweight engineering runtime that understands the task, the repository, the current execution state, the capabilities available, and the evidence required to finish cleanly.

It should combine the useful parts of:

strong engineering workflows
precise implementation policy
targeted technical context
repository/code intelligence
long-horizon execution memory
machine-enforced repository rules
dynamic verification

without combining their costs.

The important distinction is:

AVAILABLE GAUNTLET
large

ACTIVE GAUNTLET
small

3. Ultimate runtime target

A normal task might have access to:

6 strong engineering skills
hundreds of specialist rules
repository structural intelligence
technical documentation retrieval
browser verification
package knowledge
repo conventions
historical execution checkpoints
optional delegation

while actually using only:

1 skill
3 repository facts
4 relevant symbols
1 affected test

That is success.

4. Governing runtime principle

Every subsystem must answer four questions:

CHEAP PATH
What happens on an ordinary task?

ESCALATION TRIGGER
What evidence justifies doing more?

STOP CONDITION
When does this subsystem stop working?

MEASURABLE VALUE
How do evals prove that it earns its cost?

If a proposed subsystem cannot answer all four, do not make it default behavior.

6. Control owns selection

The Control Plane is the core differentiator.

It decides:

what uncertainty matters now?
what has already been established?
what has already failed?
what capability could resolve the uncertainty?
what is the cheapest sufficient capability?
is another intervention likely to change the outcome?

Do not make the system primarily tool-driven.

Bad:

Should we load a skill?
Should we query docs?
Should we use the graph?
Should we open a browser?

Good:

What could still make the current task wrong?

Then choose the smallest response.

7. Small uncertainty taxonomy

Use a small stable set.

Suggested:

INTENT
What does the developer actually require?

LOCATION
Where does the relevant behavior live?

CAUSE
Why is the observed failure occurring?

REPO_FIT
How should this repository solve this concern?

API
What does the current dependency/platform actually support?

BEHAVIOR
Does the requested behavior work?

REGRESSION
What existing behavior could this break?

SCOPE
Is the implementation doing more than required?

VISUAL
Does rendered behavior satisfy the requirement?

PERFORMANCE
Where is the meaningful cost?

Do not invent fifty uncertainty classes.

8. Uncertainty is task state, not chain-of-thought

Example:

type UncertaintyState = {
  intent: "resolved" | "open";
  location: "resolved" | "partial" | "open";
  cause: "irrelevant" | "resolved" | "open";
  repoFit: "resolved" | "open";
  api: "resolved" | "open";
  behavior: "resolved" | "open";
  regression: "resolved" | "open";
  scope: "resolved" | "open";
  visual: "irrelevant" | "resolved" | "open";
  performance: "irrelevant" | "resolved" | "open";
};

This is observable control state.

It is not private reasoning.

19. Execution State Plane

This is the major new memory improvement.

Do not treat long-running task memory as semantic retrieval over conversation history.

Use:

Execution state with explicit valid and rejected branches.

Core principle:

Memory for facts should be retrieved. Memory for work should be resumed.

20. Separate two forms of memory

Repository memory

Good for retrieval:

validation = Zod
tests = Vitest
HTTP client = src/lib/http.ts
routes normally use repositories

This is factual/structural.

Search and relevance ranking are appropriate.

Task memory

Path-dependent:

task interpreted as X
↓
hypothesis A tested
↓
A disproven
↓
cause B established
↓
implementation C chosen

This should use execution-path reconstruction.

Do not mix these into one memory mechanism.

21. Active execution path

Represent a task as a lightweight checkpoint tree.

Example:

TASK ROOT
│
├── understanding ✓
│
├── investigation ✓
│
├── implementation A ✗
│   └── rejected:
│       process-local locking is insufficient
│
└── implementation B ← ACTIVE
    ├── reuse existing coalescing primitive
    └── verification pending

The model receives the current valid root-to-active path.

It does not receive the full failed branch.

22. Failed branches are preserved but quarantined

Do not erase failures.

Do not mix them into the current state either.

Keep:

approach
reason rejected
supporting evidence

Then surface a failed branch only if current behavior begins to repeat it.

Example:

Previously rejected:
adding a second retry wrapper.

Reason:
src/lib/retry.ts already owns retry behavior.

This prevents repeated mistakes without contaminating normal context.

23. Meaningful checkpoint boundaries

Do not create a checkpoint for every shell command.

Create checkpoints when task state materially changes.

Examples:

task interpretation settled
important constraint established
root cause established
design direction chosen
approach rejected
implementation completed
verification established
verification failed materially

These are useful state boundaries.

24. Execution-state data model

Possible starting point:

type CheckpointKind =
  | "task"
  | "understanding"
  | "investigation"
  | "decision"
  | "implementation"
  | "verification";

type CheckpointStatus =
  | "active"
  | "validated"
  | "rejected";

type ExecutionCheckpoint = {
  id: string;
  parentId?: string;

  kind: CheckpointKind;
  status: CheckpointStatus;

  summary: string;

  constraints?: string[];
  decisions?: string[];

  relevantFiles?: string[];
  relevantSymbols?: string[];

  evidenceRefs?: string[];

  rejectionReason?: string;

  createdFromEvent?: number;
};

Keep it small.

25. Execution event log

Below checkpoints keep a cheap event stream.

Example:

type ExecutionEvent = {
  index: number;
  type:
    | "file_read"
    | "file_write"
    | "search"
    | "command"
    | "failure"
    | "test_result"
    | "diff_change"
    | "decision_signal";

  outcome?: string;
  evidenceRef?: string;

The event stream is not automatically sent to the model.

It supports checkpoint construction and diagnostics.

27. Machine-validation of checkpoints

Do not require an LLM to validate every checkpoint.

Prefer machine evidence.

Root-cause checkpoint might be supported by:

reproduction result
failing test
trace evidence

Implementation checkpoint:

diff exists
expected symbols changed
scope remains bounded

Verification checkpoint:

required tests pass
repo rules pass
test integrity clean

Use model validation only when semantics cannot be cheaply determined.

28. Execution-aware compaction

Replace chronological transcript summarization with boundary-aware compaction.

Ask:

Which completed section of the current valid execution path is stable enough to collapse?

Example before:

14 file reads
6 commands
3 hypotheses
2 failed edits
root-cause confirmation

After:

CAUSE ESTABLISHED

Failure:
Concurrent refresh callers independently invoke token refresh.

Cause:
Refresh operation lacks request coalescing.

Relevant:
src/auth/session.ts
src/lib/singleflight.ts

Rejected:
process-local mutex because required coordination boundary is broader.

Evidence:
race reproduction

Raw evidence remains retrievable.

29. Compaction principle

Maintain:

The current valid world, not the messy history required to discover it.

Preserve:

goal
acceptance criteria
constraints
validated facts
current approach
relevant code

Drop:

30. Branch revision

When an implementation direction is invalidated:

do not mutate history into pretending it never happened

Mark that checkpoint:

rejected

Return to the nearest valid boundary.

Create a new child branch.

Conceptually:

validated cause
├── implementation A ✗
└── implementation B ← active

This should reduce long-session spiraling.

31. Rejected-path detection

Use rejected branches as a loop guard.

If new activity resembles a known rejected direction:

new dependency duplicates rejected dependency approach
new helper resembles rejected duplicate primitive
same failed command/assertion repeats
same architecture bypass reappears

surface a small warning.

Example:

This direction overlaps with a previously rejected approach:

A second retry abstraction was rejected because the repository
already contains src/lib/retry.ts.

Reassess before creating another implementation.

No extra agent required.

35. Marginal-value context selection

Do not optimize only for relevance.

Optimize for new information.

A candidate file should be rejected if it is relevant but contributes nothing beyond existing context.

Questions:

Does it introduce a new owner?
Does it reveal another caller?
Does it expose a required interface?
Does it define an invariant?
Does it add an acceptance expectation?
Does it contradict current understanding?

If not:

leave it out

124. Core memory principle

Add this explicitly to Gauntlet's philosophy:

Memory for facts should be retrieved.

Memory for work should be resumed.

Do not summarize failed trajectories into the current state.

Branch away from them.

The active context should describe the current valid world, not the messy history required to reach it.

125. Core selection principle

Add:

The existence of a useful capability is not sufficient reason to use it.

A capability activates only when:

a relevant uncertainty exists
+
cheaper evidence is insufficient
+
activation is likely to change the task outcome

126. Core context principle

Add:

Context should be selected for marginal information, not mere relevance.

Relevant but redundant information is still waste.

127. Core code-intelligence principle

Add:

Repository understanding should grow from real development demand.

Build the neighborhood required for the task, not an exhaustive model of the repository.

128. Core evidence principle

Add:

Verification should reduce remaining uncertainty.

Do not confuse the number of checks with confidence.

129. Core workflow principle

Add:

Workflow is task state.

It should change when evidence changes.

Do not treat the skill selected at task start as permanent.

130. Core lightweightness principle

Add:

Deep capability does not justify persistent activation.

Gauntlet may contain substantial engineering intelligence while exposing only the smallest useful slice to each task.

+

+

+

+

+

132. Final governing rules

Know a lot. Load a little.

Put sophistication in selection, not in the default workflow.

Memory for facts should be retrieved; memory for work should be resumed.

Preserve the valid execution path and quarantine rejected branches.

The active context should describe the current valid world.

Context should add information, not merely relevance.

Skills control behavior.

Repository knowledge supplies local truth.

Code intelligence supplies structure.

Technical knowledge resolves platform uncertainty.

Evidence determines completion.

Use deterministic evidence before model reasoning.

Discover before building.

Observe before modifying.

Reuse before creating.

Build repository understanding progressively from actual tasks.

External documentation is an escalation, not a default.

A useful provider does not need to activate merely because it exists.

Machine-check strong repository rules when cheap.

Verification stops when additional evidence is unlikely to change acceptance.

Delegation is a rare optimization.

Silence is a first-class feature.

Every major subsystem requires:
a cheap path,
an escalation trigger,
a stop condition,
and eval evidence that it earns its cost.

And above all:

Gauntlet can know far more than it ever shows the agent.

The ultimate Gauntlet should have a very large capability surface and a very small active working set.
