GAUNTLET — COMPLETE EXPANSION & IMPLEMENTATION HANDOFF

0. Scope

This document is the consolidated build handoff for expanding the existing Gauntlet project.

Do not treat this as permission to rebuild the product from scratch.

Preserve working functionality unless a replacement clearly improves:

reliability
latency
token usage
verified completion time
clean first-pass success
maintainability

Gauntlet remains:

A lightweight control layer around coding agents that reduces unnecessary work across the software-development lifecycle.

It is not another coding agent.

It is not a methodology framework.

It is not a CI platform.

It is not a multi-agent orchestrator.

It is not a repository knowledge platform.

It is not a giant skill collection.

The core mission remains:

Do less unnecessary work at every stage of software development.

And:

Ponytail makes agents write less. Gauntlet makes agents waste less.

4. Everyday-development requirement

Gauntlet must be designed for permanent installation.

The normal developer experience should be:

↓

↓

↓
clean implementation
↓
relevant verification
↓

No additional workflow should normally be visible.

The defining runtime rule is:

Always available, rarely active.

Typical ordinary task target:

7. Core activation rule

Every optional feature should conceptually answer:

Is this relevant now?

Can cheap deterministic logic handle it?

Does the environment already provide this capability?

Can it wait until later?

Is activation likely to change the outcome?

If not:

do nothing

This is one of the most important implementation rules in the entire project.


8. Event-driven lifecycle

Prefer lifecycle events over continuous analysis.

Conceptually:

task_start
tool_activity
file_change
command_result
failure
context_pressure
before_stop
task_end

Gauntlet should respond only when a useful signal occurs.

Do not continuously ask an LLM what to do next.


9. Task contract

At task start, establish the smallest useful representation of intent.

Sources:

user request
issue text
acceptance criteria
Spec Kit artifacts
AGENTS.md
CLAUDE.md
tests
repository conventions

Example:

Goal:
Prevent duplicate token refresh.

Preserve:
- public API
- AuthError behavior

Acceptance:
Concurrent refresh calls result in one actual refresh request.

Do not generate a large planning artifact for ordinary tasks.


10. Clarification rule

Ask a question only when:

cost of guessing
>
cost of asking

Good example:

Two established behaviors exist:

A returns 409 for duplicates.
B returns the original successful response.

Which behavior should this endpoint follow?

Bad behavior:

interview user about implementation preferences

when repository evidence already answers the question.


11. Lightweight decision artifacts

For important design choices, preserve a tiny decision artifact.

Use only when the decision is likely to matter later.

Example:

Decision:
Use optimistic locking.

Reason:
Concurrent writers are expected.

Rejected:
Global mutex because application runs on multiple instances.

Do not generate formal architecture records for ordinary work unless the repository already uses them.


12. Pressure-test mode

For materially ambiguous or expensive design decisions, UNDERSTAND may temporarily become adversarial.

It should:

identify the decision that matters
challenge assumptions
surface meaningful tradeoffs
ask only decision-changing questions
stop once direction is clear

Do not activate for:

obvious bugs
small feature additions
mechanical migrations
clear acceptance criteria


13. Bounded ideation

Idea generation is useful only when divergence matters.

Use for:

greenfield behavior

Typical flow:

↓

↓
important tradeoffs
↓

↓

↓

Do not create ten variations for appearance's sake.


14. Prototype as uncertainty reduction

A prototype exists to answer a question.

Before prototyping, state:

What uncertainty are we resolving?

Then build the smallest observable experiment.

Prototype code should avoid unnecessary:

Stop once the question has been answered.

Do not silently turn prototypes into production code.

18. UNDERSTAND

UNDERSTAND

Establish what the task actually requires before implementation.

1. Identify the requested outcome.
   Separate required behavior from implementation assumptions.

2. Inspect available evidence before asking questions.
   Use repository behavior, tests, specifications, project instructions,
   task text, and established conventions.

3. Identify important constraints.
   Preserve existing public behavior, compatibility, security boundaries,
   data semantics, and repository contracts unless explicitly changed.

4. Do not invent requirements.
   Do not add speculative flexibility, configuration, future-proofing,
   or edge behavior not required by the task.

5. Resolve only material ambiguity.
   Ask one focused question when two plausible interpretations would lead
   to meaningfully different implementations.

6. If intent is sufficiently clear, proceed.
   Do not ask the user to repeat information already available in the repo.

Produce only the smallest useful task contract:
- goal;
- constraints;
- acceptance behavior;
- behavior that must remain unchanged.

Stop when interpretation error is unlikely to alter implementation.

Possible conditional techniques:

pressure testing
bounded ideation
prototyping
decision artifact


19. INVESTIGATE

INVESTIGATE

Establish the cause before changing production code.

1. Reproduce or directly observe the problem where practical.

2. Prefer strong observable evidence:
   failing tests;
   runtime output;
   traces;
   logs;
   profiling;
   concrete execution paths.

3. Trace the shortest relevant path from symptom toward cause.
   Expand outward only when evidence requires it.

4. Separate facts from assumptions.
   Verify assumptions through code, tests, types, configuration,
   package state, history, logs, or runtime evidence when cheap.

5. Prefer the earliest causal failure over downstream symptoms.

6. Do not patch error messages, retries, fallbacks, null checks,
   timeouts, or suppression merely because they hide the symptom.

7. Search for nearby helpers, invariants, conventions, and tests
   before inventing new machinery.

8. Discard hypotheses contradicted by evidence.

9. Escalate only when simple inspection fails to explain the behavior.

10. Stop when one cause is supported strongly enough to justify
    a targeted implementation.

Before editing, be able to state:
- what is failing;
- why it fails;
- where the smallest correct change belongs.


20. IMPLEMENT

IMPLEMENT

Build the smallest clear change that fully satisfies the task.

Use this decision ladder in order.

1. Does new code need to exist?
   If the requirement is already satisfied or speculative, do not add it.

2. Does this capability already exist in the repository?
   Search before writing.
   Reuse or extend code that already owns the responsibility.

3. Can the existing owning implementation be modified directly?
   Prefer direct modification over wrappers, managers, factories,
   adapters, helpers, or new layers.

4. Does the language, standard library, framework, browser,
   database, or platform already provide the capability?
   Prefer native functionality.

5. Does an installed dependency already provide the capability?
   Reuse installed dependencies before adding another package.

6. Does the environment already provide the capability through
   an installed tool, provider, or plugin?
   Use it before building another implementation.

7. Only then create new code.
   Add the minimum structure required by the actual task.

Follow active repository conventions and contracts.

Stay inside task scope.

Do not:
- duplicate existing capability;
- add speculative abstraction;
- add configuration without present need;
- introduce a second library for an existing concern;
- broaden public APIs unnecessarily;
- refactor unrelated code;
- weaken, remove, skip, or loosen tests to obtain green.

Smallest does not mean shortest syntax.
Prefer straightforward readable code.

Do not simplify away correctness, security, accessibility,
data integrity, required error handling, or acceptance behavior.

Verify unfamiliar technical facts rather than guessing.

Stop when the smallest justified solution is complete.


21. VERIFY

VERIFY

Gather enough evidence that the requested behavior works and that
meaningful risks introduced by the change are controlled.

1. Start from the task contract.

2. Ask what uncertainty remains.

3. Select the cheapest evidence capable of reducing that uncertainty.

Prefer, where relevant:
- compile/typecheck;
- impacted tests;
- static checks;
- active repository gates;
- changed-behavior scenarios.

4. Verify behavior, not merely execution.

5. Inspect modified tests for:
- deletion;
- skipping;
- weakened assertions;
- broadened tolerances;
- unjustified expected-output changes;
- mocks that remove the behavior being tested.

6. Add targeted evidence only where meaningful uncertainty remains.

Possible techniques:
- boundary tests;
- negative permission/security cases;
- property/generated cases;
- targeted mutation;
- counterfactual failure checking;
- integration checks;
- browser verification;
- E2E where the actual risk crosses that boundary.

7. Prefer repository-native tools.

8. Treat tests, coverage, mutation, lint, static analysis,
   and browser checks as evidence rather than absolute truth.

9. Stop when additional verification is unlikely to change
   the acceptance decision.

Report concrete evidence.
Do not report invented confidence percentages.


22. REVIEW

REVIEW

Review only problems introduced by this change.

Check for:

1. unnecessary scope;
2. duplicate capability;
3. unnecessary abstraction;
4. unjustified dependency growth;
5. repository-contract violations;
6. convention drift;
7. test degradation;
8. accidental public API growth;
9. dead or speculative code;
10. meaningful complexity growth;
11. baseline regressions.

Ignore unrelated pre-existing debt.

Do not report vague preferences such as:
"could be cleaner"
or
"consider refactoring."

Report only concrete issues worth fixing.

If there is no meaningful issue, do not invent one.


23. OPTIMIZE

OPTIMIZE

Improve what is measurably expensive.

1. Establish a baseline.

2. Identify the dominant relevant cost.

3. Trace the smallest cause responsible for that cost.

4. Prefer local improvement over architectural redesign.

5. Preserve behavior unless change is explicitly permitted.

6. Prefer deletion or simplification when it removes real cost.

7. Measure again after the change.

8. Compare against the baseline.

9. Keep added complexity only when the improvement justifies it.

10. Stop once the dominant relevant cost has been addressed.

Possible metrics:

runtime
latency
memory
query count
build time
test time
bundle size
context/token consumption
tool execution

40. Non-regression baselines

Record only task-relevant baseline measurements.

Examples:

lint issue count
skipped tests
dependency set
public exports
architecture violations
repository-rule violations

Principle:

Existing debt may remain. New work should not quietly worsen it.

Example:

lint:
12 → 12 pass
12 → 11 improvement
12 → 13 regression

Do not require fixing the original 12.


41. Baseline selection must be dynamic

If package.json did not change:

dependency baseline may be unnecessary

If no tests changed:

deep test-delta analysis may be unnecessary

If public API untouched:

export baseline unnecessary

Do not calculate everything every task.


42. Counterfactual verification

When a new behavior-specific test/check is created, Gauntlet may verify that it can actually detect the intended failure.

When cheap:

new test
↓
run against broken/pre-change behavior
↓
should fail
↓
run against fixed behavior
↓
should pass

If:

old behavior → PASS
new behavior → PASS

the test is weak evidence.

Use selectively.


43. Counterfactual verification triggers

Useful for:

new regression tests
high-risk fixes
generated acceptance tests
important architecture checks
suspiciously weak tests

Skip when:

old revision cannot run safely
environment setup is expensive
reverting creates risk

Never pretend it succeeded if it was skipped.

148. Research lessons distilled

Research inputs suggest the following underlying principles.

Ponytail:

precise behavioral policy can strongly alter agent implementation choices

Gap-Trap:

important rules should be independently machine-checkable where cheap

Superpowers:

structured engineering behavior helps, but process should scale with task complexity

RTK:

raw command output is often mostly context waste

tgrep:

repository search infrastructure matters on large codebases

Deep Agents:

context/state/offloading are first-class harness concerns

find-skills:

discover capability before creating it

grill-style skills:

pressure-test expensive uncertainty, not every task

prototype workflows:

building a small experiment can resolve uncertainty faster than discussion

diagnostic skills:

observe signal and establish cause before patching

frontend/image workflows:

rendered output is evidence for visual tasks

skill-creator:

skills require evals, especially trigger evals

subagent workflows:

isolated context can help, but coordination has real cost

agent-tool builders:

tools should be designed for agent task completion, not mechanical API exposure

React/Postgres expert packs:

domain rules should be prioritized by expected impact

UI knowledge systems:

large expert knowledge should be searchable and selectively loaded

brand systems:

stable visual/product truth should not be rediscovered every task

visual-polish systems:

combine deterministic defects with bounded rendered review

SEO audits:

audit high-impact failure classes first

browser systems:

browser capability should be a provider, not core infrastructure

component registries:

reuse and preview generated changes before creating custom replacements

Relay-style delegation:

event-driven completion beats polling

150. Final architecture philosophy

Gauntlet should behave like a lazy runtime for engineering intelligence.

It should be:

installed permanently
cheap by default
context-aware
evidence-driven
repository-aware
provider-friendly
harness-neutral
precise when activated
silent when unnecessary

The size of Gauntlet's available intelligence may grow.

The size of the active Gauntlet working set should stay small.

That distinction is essential.


151. Final governing rules

Make intelligence deep, but activation sparse.

Use deterministic evidence before model reasoning.

Discover before building.

Observe before modifying.

Reuse before creating.

Preserve state, discard stale transcript.

Compress context, never evidence.

Turn only strong repository conventions into enforceable rules.

Existing debt may remain; new work should not silently worsen it.

Verification should answer remaining uncertainty, not execute every possible check.

Domain expertise should be searchable and selectively loaded.

Visual behavior should be judged from rendered evidence when practical.

Delegation should be rare, isolated, event-driven, and parent-verified.

Harness-specific optimizations belong behind capability detection.

Skills are code: evaluate their triggers and outcomes.

Silence is a feature and must be tested.

Every Gauntlet mechanism must save more expected failure, rework, compute, latency, tokens, cost, or human attention than it adds.

And above all:

Gauntlet should improve the development workflow without becoming another workflow developers have to manage.
