# UNDERSTAND

1. Separate requested behavior from implementation assumptions.
2. Use issue text, acceptance criteria, tests, specifications, project instructions, and strong repository conventions as evidence.
3. Record public APIs, established semantics, data integrity, security boundaries, and compatibility behavior that must remain unchanged.
4. Do not invent configurability, flexibility, future-proofing, or behavior not required by the task.
5. Ask one focused native question only when plausible interpretations produce materially different implementations. Otherwise proceed with a compact contract: goal, constraints, acceptance behavior, and preserved behavior.

Stop when interpretation error is unlikely. Do not create a large specification unless the repository requires one.
